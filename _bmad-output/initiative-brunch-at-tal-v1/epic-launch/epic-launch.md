# E6 השקה: בדיקות קבלה, יבוא, פרודקשן ותפעול

## Description

שלב 6 בסדר הבנייה: בדיקות הקבלה המלאות, יבוא לקוחות אם נדרש, תוכן אמיתי, גיבוי ובדיקה תפעולית עם טל לפני השקה. בסוף האפיק המערכת רצה בפרודקשן נפרד, עם תוכן שטל הזינה, לקוחות מיובאות שקיבלו קישור הפעלה, וגיבוי שנבדק, והאתר נפתח לציבור.

## Outcome

טל פותחת את העסק באתר החדש, וה-Success signal של ה-SPEC מתקיים בפרודקשן: תשלום, הצטרפות, הרשמה וביטול, בלי רשומה כפולה או אבודה.

## Requirements

- CAP-31: יבוא לקוחות קיימות עם יתרות, וקישורי הפעלה אישיים.
- E6-R1: כל בדיקה ב-`acceptance-criteria.md` עוברת מול מסד Supabase אמיתי של סביבת בדיקה. (SPEC › Success signal, §11)
- E6-R2: ההשלמות לפני השקה ב-`build-sequence.md` הושלמו או נשארו בטיוטה בלי תוכן מומצא. (build-sequence.md › השלמות לפני השקה, §12)
- E6-R3: פרויקט פרודקשן נפרד, repo פרטי ותוכנית Vercel בתשלום, לפני יבוא או תוכן אמיתי. (AGENTS.md, spine Deferred, AD-22)
- E6-R4: גיבוי חיצוני ושחזור. (§11 שלב 6, spine Deferred)
- E6-R5: בדיקה תפעולית עם טל, ופתיחה לציבור (הסרת ה-noindex) רק אחרי שהגבלת הקצב פעילה. (§11 שלב 6, spine Deferred)

## Done when

1. כל סעיף ב-`acceptance-criteria.md` ממופה לבדיקה אוטומטית או ידנית, וכולן עוברות מול מסד הבדיקה. הדוח נשמר.
2. פרויקט Supabase לפרודקשן קיים, קיבל את כל ה-migrations ב-`supabase db push`, וה-advisor שלו נקי. ה-repo פרטי, ו-Vercel בתוכנית בתשלום.
3. אם יש לקוחות קיימות: הן יובאו, היתרות תואמות לקובץ, מי שהשתתפה לא מקבלת היכרות, והתנגשויות דווחו. לכל אחת יש קישור הפעלה עם סטטוס.
4. גיבוי חיצוני קיים, ושחזור ממנו לפרויקט בדיקה עבר פעם אחת.
5. טל עברה את ה-Success signal בפרודקשן בטלפון שלה, והאתר נפתח לציבור.

## Boundaries

השקה, יבוא ותפעול. היכולת החדשה היחידה היא יבוא הלקוחות (CAP-31). תקלה שנמצאת בבדיקות הופכת לבאג (`bug`) באפיק שבנה את היכולת, או כאן אם האפיק כבר נסגר. לא סבב הסליקה.
